# Mac second-target tooling rollout

The byte-comparison and call-report tooling is implemented. The initial
checkpoint below predates the removal of duplicate headers; its scores and
worker authorization are historical. Reviewed Mac addresses now cover most
non-exact game functions, and Windows matching is underway. Ordinary-header
compilation status is recorded in the
[native-header status](mac-native-headers.md).

## Required end state

- `homm3 build --fast <TU>` compiles shared authored C++ for VC6 and CodeWarrior
  wherever a verified Mac counterpart is supported. A full build checkpoints
  both targets and runs their gates.
- Every compared function has a pinned target, verified boundaries, a source
  owner, compiler/profile provenance, and resolved reference identities.
- Reports compare retail and candidate **call sites and ordered targets**,
  alongside bytes and scores. Counts are static instructions, not runtime
  execution counts or proof of inlining. Indirect calls and unknown targets
  remain explicit.
- An actionable queue covers unfinished game functions and distinguishes
  missing pairing, missing compilation support, unresolved references, call
  differences, and remaining instruction differences. Zero observed calls is
  distinct from an unavailable candidate or missing Mac counterpart.
- Queue entries carry the evidence/inspection command, owning source, scope,
  current observations and next step needed by a matcher. Stale observations
  cannot become dispatch-ready work.
- Coverage is counted separately from match percentage. An exact pilot set
  does not establish whole-game Mac coverage.

## Queue routing

Builds refresh the call report and queue automatically. A failed pair does not
hide later pairs: its unavailable candidate or byte-comparison error remains
in the call report. Incomplete Mac passes cannot checkpoint a partial MAX ledger.

Useful commands:

```sh
homm3 mac calls                         # all admitted retail/candidate call sequences
homm3 mac queue                        # all unfinished game tasks; show the first 20
homm3 mac census                       # unclassified code scan and reviewed-pair coverage
homm3 mac find --field 0xd8 --field 0xd7 --field 0xd9 --field 0xda
homm3 mac find --string "heroWindow"
homm3 mac xrefs mac:1:0x44bd4            # loader pointers and code uses of a data object
homm3 mac xrefs 0x004da3a0               # incoming branches to an admitted counterpart
homm3 mac disasm mac:0:0xf6290 --size 0x40
```

Search windows and unclassified branch-pattern scans are discovery leads.
They can cross functions or contain inline data, and do not admit boundaries.
Raw disassembly requests must supply an explicit size.

1. **Pairing needed:** locate a Mac counterpart through reviewed strings,
   constants, field accesses, call graph and data references. Admit its span
   only after identity and boundaries have evidence.
2. **Compilation needed:** establish the Mac declarations, ABI and required
   shared definitions, then compile the owning source. Never duplicate the
   function body in a shim.
3. **Reference resolution needed:** identify unknown call/data/import targets.
   A compiler-emitted call can still be counted before its address is known;
   it cannot support an exact-byte verdict.
4. **Calls differ:** inspect the ordered named calls and specific added/removed
   targets. Recover canonical helper boundaries and visibility before making
   inlining hypotheses. Equal counts alone do not close this task.
5. **Calls agree, bytes differ:** inspect Mac instruction differences and
   shared-source evidence, then validate each later source change in both
   compilers. Indirect-call destinations may remain unproven.
6. **Mac exact, Windows unfinished:** use the Mac result as additional source
   evidence while investigating VC6 code generation and possible port changes.

The user-deferred `rmg`, `zlib-1.1.3`, `codec` and `victor` modules remain visible
as deferred work. They must not silently disappear from coverage or enter the
active matching queue by default.

## Constraints and limits

Source `VA(...)` and `DATA(...)` annotations own identities and names. Mac
addresses are PEF section plus offset. Reviewed manifests pair those identities
with target spans; compiler-generated constants use verified payloads, not
unstable temporary symbol numbers.

The shared compiler harness records `paired_bodies_in_source_order`. A unit
profile supplies shared Mac declarations and can expose additional source-owned
helpers by VA; canonical inline bodies can come from compatible project headers.
Every compiled game body comes from its owning source. This scope does not
claim that omitted Windows platform code or libraries have been ported.
Unresolved callees and data references still prevent an exact verdict.

`config/mac/references/<TU>.toml` admits callee identities independently of
their compilation support. Each `[[functions]]` row carries the source Windows
VA, owning unit, complete Mac span, SHA-256 and pairing
evidence. Names come from the owning source annotation, including annotated
forward declarations. Omit `mac_symbol` while locating addresses. Such entries
appear in `mac labels` as `address_reference_only`; `mac show` and `mac disasm`
accept their Windows VA or source name immediately. A reviewed address is not
a compiled comparison. Once the emitted CodeWarrior symbol is verified, adding
`mac_symbol` lets the reference resolve candidate calls. References never enter
the byte-score denominator; scored pairs remain separately admitted.

Reviewed `VA_COMPGEN` class constructors/destructors and typed `VECTOR_DTOR`
annotations can also own address references. Vector destructor references are
address-only: their different standard-library implementations require separate
compiler-binding work before they can resolve candidate calls.

TU/source order narrows the search. Confirm each identity using calls, field
accesses, constants, strings or vtables and review its boundaries before recording
it. Retained helpers, template instances and cleanup bodies can intervene; do not
zip the two function lists by ordinal position. Record unresolved leads under
ignored `build/mac/address-discovery/`, keeping only reviewed spans in manifests.
For an annotation owned by a header, set `source = "include/...h"` (or a
registered `.inl` fragment). The reference resolves the canonical claim there;
it does not require a duplicate VA annotation in the TU.

For a canonical ordinary helper without an established Windows VA, use a
`[[helpers]]` reference with `source_helper = "name"` (or `"Class::method"`),
`unit`, and the same Mac span, symbol, hash and evidence fields. Do not supply
`retail_va`. The selector must locate exactly one supported definition in the
owning TU or registered fragment; declarations, ambiguous overloads and
unsupported scopes fail.
Keep in-class helper bodies in their ordinary owning headers. CodeWarrior
reads those definitions directly through the source include prefix; do not
extract them into fragments or add duplicate out-of-class definitions. A
reference identity that tooling cannot yet resolve remains an explicit gap.
To select an overload, append its exact authored parameter declaration,
including parameter names and trailing `const` (whitespace is ignored), for
example `"Owner::set(TCreatureType newType, short* newAmount)"`.
`source_helpers = ["name"]` in the unit profile exposes that exact body in
authored source order. These references are labeled
`source_helper_reference_only`, outside Windows inventory and byte scores.

`config/mac/data/<TU>.toml` uses the shared data inventory schema. A
`declaration_only = true` row identifies external storage through its source
`DATA` annotation and reviewed Mac loader/TOC evidence. Its digest verifies the
address anchor, not a candidate initializer or the complete object's extent.
Definitions, externs and reference-to-array declarations can own this identity.
TU-static definitions can also bind external storage in the comparison group.
For a class-static member, place DATA on its canonical declaration and supply
the emitted `mac_symbol` in its declaration-only row. Its qualified source
name is derived from the enclosing class; the Mac class view supplies the
declaration, without injecting an out-of-class definition or initializer.
An emitted candidate initializer cannot silently use this address-only path.
An externally emitted CodeWarrior vtable can use a separate reviewed
`config/mac/vtables/<TU>.toml` binding when the object contains only a TOC
cell. The binder checks the canonical and Mac virtual declarations, full
retail table and RTTI hashes, the loader pointer to the table, and every
transition-vector and code-body link. It does not construct or score an
initializer from retail bytes; emitted candidate table payloads remain
unsupported.
When a global is actually defined in the compiled source TU and the Mac code
uses its direct TOC address, set `same_tu_definition = true` instead of
`declaration_only`. The source must contain one ordinary uninitialized DATA
definition such as `DATA(...) std::string g_resourcePath;`; list that VA in the
pair's `data` so the exact authored definition is compiled with the body.
The reviewed Mac storage bytes and emitted candidate storage still have to
agree. This option does not create a second source definition or claim a
runtime initializer match.
Use `units = ["<TU>"]` on literals when their equal payloads occur in distinct
linked pools; ambiguity remains an error. Identical worker data entries
coalesce and conflicting entries fail validation.
When several anonymous literals have the same payload inside one function,
add `owner_va`, `candidate_offset` and `target_offset` to each `[[constants]]`
row. The offsets are relative to the emitted MWOB hunk and the admitted Mac
function respectively. The resolver requires one anonymous reference at the
candidate site. A direct reference must load the declared TOC address; an
indirect reference must load through the exact retail TOC cell whose loader
pointer reaches the declared payload. Both forms check the target instruction
against the pinned PEF. An edit that moves an emitted use
must update its reviewed candidate offset before the comparison can run.
If one emitted literal is referenced more than once, list every use site;
unreviewed uses fail the comparison.
Reviewed anonymous literals may reside in a PEF code section. They still
require an exact payload/hash and a loader-proven TOC pointer; a code-section
location does not authorize arbitrary named storage or direct cross-section
TOC addressing.
Named const objects and arrays may also occupy code-section pools. Constness
is derived from the supported canonical declaration, never a manifest flag;
pointer-to-const and reference declarations do not take this route.

Library-owned data named by the pinned CodeWarrior headers uses a separate
`[[data]]` row in `config/mac/runtime.toml`, with its emitted symbol, reviewed
Mac section/offset/size/hash and evidence. The Mac view declares the same
external symbol; the resolver requires its candidate IL/TC reference and the
retail loader pointer. This binds a runtime address without claiming a game
source DATA owner or comparing a fabricated initializer. For example, MSL's
inline `toupper` reads the reviewed 256-byte `__upper_map` table.

Library call targets use pinned `[[functions]]` rows in the same runtime
manifest; source-owned external callees use `config/mac/references/`. For
`ResourceManager::open`, the vector constructor/reserve/pop/destructor and
exception runtime rows plus the source-owned `LODFile::clear` reference now
resolve all 13 direct calls on both sides, in the same order. Its current
528-byte Mac target and 508-byte candidate score 28.41%; this is an actionable
body comparison, not a call-resolution gap.

A function-local `static const` DATA initializer uses `owner_va` to identify
its enclosing authored function. The emitted `name$counter` is resolved by its
source name and exact reviewed payload, without pinning the compiler's counter
or injecting another global definition.

Reviewed `[[jump_tables]]` records bind compiler-generated dispatch tables by
owning function, complete span/hash and retail TOC reader. All words must
relocate to instructions within the owner. Candidate labels are rebased after
reload removal, and code plus table bytes determine the score and exact verdict.
See the [report's verdict definition](mac-matching-report.md#what-an-exact-result-means)
for the report fields and current supported form.

CodeWarrior's `TB` exception tables are printed symbolically by its disassembler.
The harness records their extents and references separately in
`compilation.json`, with `comparison = "not_compared"`. Function verdicts cover
resolved code and reviewed switch-table bytes. They do not claim matching exception metadata or external
initializers. Malformed metadata extents still fail extraction.

`homm3 mac campaign --workers 6` writes `build/mac/campaign.json`. Each packet
owns one TU and starts with up to three targets; all other functions remain in
the queue. Packets distinguish matching from establishing Mac evidence. A
preparation packet never relabels an unsupported function as match-ready.

Dreamcast remains a source-fact reference for names, declarations and line
evidence. Mac is the second exact byte target and the primary additional view
of retained helper calls. Neither allows overriding contrary retail evidence.

See [the target design](../matching/mac-second-target-plan.md) for pinned inputs,
compiler calibration, current admitted pairs and exact-comparison constraints.


## Extending a unit

For a reviewed address reference that is not yet an admitted exact pair, add
the unit's compiler profile and run `homm3 mac shape <Windows-VA>`. This compiles
the ordinary source and headers with CodeWarrior, then aligns its instructions
with the pinned PEF while masking TOC displacements and branch targets. It
reports retained direct calls in source and retail order. No global-data or
callee relocation manifest is needed for this source-shape pass. Its assumed
linker reload-slot collapse and masked addresses cannot establish an exact Mac
byte verdict; use `homm3 mac diff` for that stricter comparison when needed.

1. Create `config/mac/units/<TU>.toml` with compiler settings:

   ```toml
   mode = "paired_bodies"
   flags = ["-O1", "-proc", "750", "-nolink"]
   helpers = [] # optional additional source-owned VA definitions
   ```

   Calibrate flags against that unit's Mac code. Preserve real helper calls,
   declarations, body visibility and source order. Candidate inputs preserve
   the source file's include prefix and read the ordinary game headers. Native
   MSL headers are staged with `homm3 mac sdk PATH`. Missing platform headers or
   compiler errors remain explicit coverage gaps. Do not add replacement game
   declarations or extracted header bodies.

2. Run `homm3 mac compile <Windows-VA> --unit <TU>`. This exposes emitted
   MWOB hunk names, sizes and references under `build/mac/objects/probe-<VA>/`.
   It does not admit a target or write a score. Inspect Mac pairing leads and
   verify identity and both boundaries before admission.

3. Prepare a proposal, then repeat with `--admit` after reviewing the evidence:

   ```sh
   homm3 mac pair <Windows-VA> --unit <TU> --at mac:0:<offset> \
     --size <bytes> --symbol '<emitted-symbol>' \
     --evidence 'Identity anchors and boundary evidence'
   ```

   Proposals go to ignored `build/mac/pairing/`. Admission writes
   `config/mac/functions/<TU>.toml`, validates ownership and overlapping spans,
   and records the target-byte hash. `--data <Windows-DATA-VA>` includes an
   already reviewed source-owned initializer. Runtime and anonymous data
   additions need their own reviewed evidence in the existing manifests.

4. Run `homm3 build --fast <TU>`, `homm3 mac calls <Windows-VA>` and
   `homm3 mac diff <Windows-VA>` (`--json` includes the complete verdict and
   provenance). Address explicit compilation/reference prerequisites first.
   Inspect `build/mac/objects/unit-<TU>/compilation.json` for emitted coverage.

5. Review collateral in both targets, then run the full build for checkpoint
   and gates. Unit builds preserve other units' observations; the queue checks
   each observation's original source, profile, artifact and analysis hashes.


## Initial tooling checkpoint

The full integrated build passed after grouped compilation, import/indirect
call handling, per-unit admission and concurrent report publication were added.
All 65 relevant tooling tests passed. Real CodeWarrior/MWLink controls reproduce
40-byte imported, 48-byte function-pointer and 48-byte virtual-call bodies,
including every branch and TOC restore. The five shared hero pairs retain
four exact results and the unchanged 96.7391% source candidate.

The initial queue contains 518 unfinished tasks: 432 need Mac pairing, 85 are
user-deferred, and one has a fresh Mac instruction difference. Four further
admitted pairs are already exact in both ledgers. This is tooling readiness
with explicit coverage gaps; it is not whole-game Mac completion. The first
wave includes setup/pairing work before matching in units without counterparts.

The six-worker wave now extends that initial inventory. Its focused reports
can contain both scored functions and explicit setup failures while additional
callees and globals are admitted. The README figures identify the last complete
checkpoint; `homm3 mac queue` validates current observations before dispatch.
Subsequent resolver controls reproduce all 40 bytes of two separately linked
external-global functions, including MWLink's address-load relaxation. Runtime
bindings for `memcpy`, `strcpy` and `sprintf` were checked against the named
CodeWarrior MSL library hunks, including their complete emitted extents.
